## Unit 1: Java Basics, OOP Fundamentals, and Class Design

### Q1: Why does caching improve application performance, and what is an in-memory cache?
**Answer**: Caching improves performance by storing frequently accessed data in high-speed storage so future requests are served faster than fetching from slow secondary storage such as hard drives or remote databases. An in-memory cache keeps key-value pairs directly in RAM, achieving sub-microsecond access latencies (\(O(1)\)) compared to millisecond-level disk or network I/O. In our project, the core cache engine lives entirely in RAM within `ThreadSafeCache` ([`com.cse309.cache.core.ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java)). Persistent stores like SQLite are only touched out-of-band for durable backups, never on the hot path.

### Q2: What is the fundamental difference between an abstract class and an interface in Java?
**Answer**: An interface defines an API contract of methods that implementing classes must satisfy and supports multiple inheritance of type. An abstract class cannot be instantiated directly, may hold shared mutable or immutable state (instance fields), constructors, and template method implementations, but is constrained by single inheritance. In our architecture, [`Cache<K,V>`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/Cache.java) is a pure generic interface defining the cache contract. In contrast, [`AbstractCache<K,V>`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/AbstractCache.java) provides shared state (such as capacity, listeners, and statistics) and implements skeletal methods like `isEmpty()` and `putWithoutExpiry()`.

### Q3: What are the three distinct uses of the `final` keyword in Java, and where do they appear in your project?
**Answer**: In Java, `final` applies to variables, methods, and classes. A `final` variable cannot be reassigned after initialization, ensuring immutability as seen in all fields of [`CacheEntrySnapshot`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/CacheEntrySnapshot.java). A `final` method cannot be overridden by subclasses, preserving template method invariants such as `getStatistics()` in [`AbstractCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/AbstractCache.java). Finally, a `final` class cannot be extended, sealing concrete implementations against subclassing, as demonstrated by [`ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java) and the eviction policies [`LeastRecentlyUsedPolicy`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/eviction/LeastRecentlyUsedPolicy.java).

### Q4: How does constructor chaining with `this(...)` work, and why is it beneficial?
**Answer**: Constructor chaining with `this(...)` allows one constructor in a class to invoke another constructor in the same class, passing default arguments to a single canonical constructor. This pattern eliminates duplicate initialization logic and ensures all invariants are validated in one centralized location. In our codebase, [`CacheConfiguration`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/config/CacheConfiguration.java) chains its default parameterless constructor to an overloaded constructor, which in turn calls the master 8-parameter constructor with validated defaults.

### Q5: How do access specifiers (`public`, `protected`, package-private, `private`) enforce encapsulation in your system?
**Answer**: Our system utilizes all four Java access specifiers with deliberate intent. `public` exposes external interfaces and models like [`Cache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/Cache.java) and [`CacheWriteResult`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/CacheWriteResult.java) to UI and clients. `protected` provides subclass extension points, such as listener notification hooks in [`AbstractCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/AbstractCache.java). Package-private visibility (no modifier) encapsulates mutable internal representations like [`CacheEntry<V>`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/CacheEntry.java), preventing external classes from modifying live cache entries directly. `private` hides internal locks, collection pointers, and helper algorithms entirely.

## Unit 2: Polymorphism, Exception Handling, Object Class & Generics

### Q6: What is the difference between method overloading and method overriding?
**Answer**: Method overloading (compile-time polymorphism) occurs when multiple methods in the same class share a name but differ in their parameter lists (number, type, or order), resolved at compile time based on static types. Method overriding (runtime polymorphism) occurs when a subclass provides a specific implementation of a method already declared in its superclass or interface, resolved dynamically at runtime via virtual method dispatch. In [`Cache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/Cache.java), overloading is shown by `put(K, V)` and `put(K, V, Duration)`. Overriding is demonstrated by [`ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java) overriding all abstract methods of `AbstractCache`.

### Q7: How does runtime polymorphism enable dynamic eviction policy switching?
**Answer**: The cache engine holds an abstract reference to the generic interface [`EvictionPolicy<K>`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/eviction/EvictionPolicy.java). At runtime, when the user selects LRU, FIFO, or LFU, the engine instantiates the corresponding concrete policy (`LeastRecentlyUsedPolicy`, `FirstInFirstOutPolicy`, or `LeastFrequentlyUsedPolicy`) and calls `policy.rebuild(entries)`. The engine invokes `policy.onAccess(key)` or `policy.selectVictim()` without knowing which concrete class is active. Dynamic method dispatch ensures the JVM automatically routes the call to the appropriate algorithm at runtime.

### Q8: What is the difference between checked and unchecked exceptions, and how is your hierarchy designed?
**Answer**: Checked exceptions (subclasses of `Exception` excluding `RuntimeException`) are verified at compile time, forcing callers to either catch them or declare them with `throws`, making error recovery explicit. Unchecked exceptions (`RuntimeException` and `Error`) represent programming errors or unrecoverable environmental faults. In our project, all business and persistence failures extend the root checked exception [`CacheException`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/exception/CacheException.java). This root class defines both a technical diagnostic message (`getMessage()`) and an end-user explanation (`getUserMessage()`) so dialogs never present raw stack traces.

### Q9: What are multiple catch blocks and multi-catch (`A | B e`), and where do they appear in the project?
**Answer**: Multiple catch blocks allow handling different exception types thrown from a single `try` block with distinct recovery logic, evaluated from most specific subclass to most general superclass. Multi-catch (`catch (IOException | SQLException e)`) allows multiple unrelated exceptions to be caught and handled with identical logic in a single catch block without duplicating code. In [`SnapshotFileManager`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/SnapshotFileManager.java), the `load` method uses separate catch blocks to distinguish `FileNotFoundException`, `EOFException` (truncated files), and `UTFDataFormatException`, and wraps them in [`SnapshotFormatException`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/exception/SnapshotFormatException.java).

### Q10: Why should `finalize()` never be used in modern Java, and what constructs replace it?
**Answer**: `finalize()` is deprecated and terminally condemned because its invocation by the garbage collector is completely unpredictable, non-deterministic, can cause object resurrection, and severely degrades GC throughput. Resource cleanup must be performed deterministically using `AutoCloseable` combined with try-with-resources. In our project, database connections and file streams in [`DatabaseManager`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/DatabaseManager.java) and [`SnapshotFileManager`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/SnapshotFileManager.java) are managed exclusively through try-with-resources, guaranteeing prompt resource release even when exceptions occur.

### Q11: How are the `equals()`, `hashCode()`, and `toString()` methods correctly overridden?
**Answer**: Whenever `equals()` is overridden, `hashCode()` must also be overridden to satisfy the contract: if two objects are equal according to `equals()`, their hash codes must be identical. In [`Student`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/lab/Student.java), equality is evaluated on student ID and department, and `Objects.hash(id, department)` produces consistent hash codes. `toString()` is overridden to provide human-readable representations for logging and UI inspection. In [`CacheEntrySnapshot`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/CacheEntrySnapshot.java), `equals()` checks the key and insertion sequence to verify snapshot identity.

### Q12: What is generic type erasure, and how do wildcards (`? extends` and `? super`) improve API usability?
**Answer**: Type erasure is the compile-time mechanism where the Java compiler replaces generic type parameters with their bounds (or `Object` if unbounded) and inserts necessary casts, preserving backwards compatibility with legacy JVM bytecode. Wildcards provide flexibility under the PECS rule (Producer Extends, Consumer Super). In [`Cache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/Cache.java), `putAll(Map<? extends K, ? extends V> entries)` allows putting a map whose keys and values are subtypes of the cache's types. In [`CollectionTools`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/CollectionTools.java), the bounded generic method `<T extends Comparable<? super T>>` operates on any self-comparable element.

## Unit 3: Concurrency, Multithreading, I/O & Event Handling

### Q13: What is the difference between extending `Thread` and implementing `Runnable`?
**Answer**: Extending `Thread` creates a custom thread class where `run()` is overridden directly, but consumes the class's single inheritance hierarchy. Implementing `Runnable` separates the task (the code to execute in `run()`) from the execution mechanism (the `Thread` instance), promoting clean OOP design and enabling reuse. In our architecture, [`WorkerThread`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/WorkerThread.java) extends `Thread` to maintain dedicated per-worker state (e.g. processed counts and uncaught exception handlers). Meanwhile, [`OperationProducerTask`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/simulation/OperationProducerTask.java) implements `Runnable` to generate operations into a bounded buffer.

### Q14: What are the six Java thread states (`Thread.State`), and where can they be inspected in the UI?
**Answer**: The six thread states defined in `java.lang.Thread.State` are `NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`, and `TERMINATED`. In our application, [`ThreadStateMonitor`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/ThreadStateMonitor.java) periodically samples worker threads using `Thread.getState()`. The Simulator Tab renders these live states in a dedicated `ListView`. During simulation, workers alternate between `WAITING` (waiting for tasks in the buffer), `RUNNABLE` (executing cache operations), and `TIMED_WAITING` (pauses or timed waits).

### Q15: What is the difference between calling `thread.start()` and `thread.run()`?
**Answer**: Calling `thread.start()` requests the operating system and JVM to allocate a new native execution thread, creates a separate call stack, and invokes the `run()` method asynchronously on that new thread. Calling `thread.run()` directly merely executes the method synchronously on the caller's current thread like a standard method call, without creating any concurrency. In [`WorkerPool`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/WorkerPool.java), `startAll()` calls `worker.start()` on each worker thread to spawn concurrent background threads.

### Q16: How does `Thread.sleep()` differ from `Object.wait()`?
**Answer**: `Thread.sleep()` is a static method that suspends the current thread for a specified duration without releasing any synchronization locks it currently holds. `Object.wait()` is an instance method that must be called from inside a `synchronized` block on the target object; it atomically releases the monitor lock and suspends the thread until another thread calls `notify()` or `notifyAll()` on that same object. In [`BoundedBuffer`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/BoundedBuffer.java), `wait()` is used so producers and consumers release the buffer lock while waiting.

### Q17: Why must `wait()` always be invoked inside a `while` loop rather than an `if` block?
**Answer**: Calling `wait()` inside a `while` loop protects against two critical concurrency hazards: spurious wakeups (where the OS wakes a thread without any notify call) and state changes by other threads. In a multi-consumer system, when `notifyAll()` wakes multiple waiting threads, the first thread to re-acquire the lock may consume the available item. If subsequent threads woke up from an `if` statement, they would proceed with an invalid condition (e.g. empty buffer), leading to corrupted state or index out of bounds errors. The `while` loop forces the thread to re-test the condition before proceeding.

### Q18: Why is `notifyAll()` preferred over `notify()` in `BoundedBuffer` and `PauseGate`?
**Answer**: `notify()` wakes a single arbitrary thread from the object's wait set, while `notifyAll()` wakes all waiting threads. If `notify()` is used when multiple thread groups (e.g., both producers and consumers) wait on the same monitor, a producer might signal another waiting producer instead of a consumer, leading to a permanent deadlocked stall where all threads wait forever. In [`BoundedBuffer`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/BoundedBuffer.java) and [`PauseGate`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/PauseGate.java), `notifyAll()` guarantees that every thread re-evaluates its wait condition.

### Q19: What is a race condition, and what is a deadlock?
**Answer**: A race condition occurs when two or more threads concurrently access shared mutable data and the final outcome depends on the non-deterministic interleaving of thread execution, resulting in lost updates or corrupted data. A deadlock occurs when two or more threads are permanently blocked, each holding a lock that the other needs, creating a circular wait dependency. In [`RaceConditionLab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/lab/RaceConditionLab.java), we demonstrate race conditions in `UnsafeCounterBox`, and prove how `SafeCounterBox` prevents them using synchronization.

### Q20: Why did you choose a single private lock over `ReentrantReadWriteLock` for the cache engine?
**Answer**: Under LRU and LFU policies, a `get(key)` operation mutates internal state: it alters the access sequence in LRU and increments access frequency in LFU. Because `get` is fundamentally a write to eviction metadata, a `ReentrantReadWriteLock` would require acquiring the exclusive write lock on every single lookup anyway, completely negating any concurrency benefit of read locks while adding significant overhead. A single private lock using Java's built-in `synchronized` keyword provides simpler, faster, and provably leaf-lock deadlock-free execution in [`ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java).

### Q21: Why is the engine lock guaranteed to be deadlock-free?
**Answer**: Deadlock requires four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, and circular wait. Our cache engine follows strict leaf-lock discipline: while holding the private engine lock in [`ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java), no external callbacks, no database I/O, no filesystem operations, and no secondary lock acquisitions are ever performed. Because the thread holding the cache lock never waits for any other lock or resource, circular wait is mathematically impossible, guaranteeing absolute freedom from deadlocks.

### Q22: What is the difference between `volatile` and `synchronized`?
**Answer**: `volatile` guarantees memory visibility and ordering (preventing instruction reordering) so that reads and writes to a field are always observed by all threads directly in main memory, but it does NOT provide atomicity for compound operations like `count++`. `synchronized` provides both memory visibility and mutual exclusion (atomicity), ensuring that only one thread can execute a critical section at any given time. In [`SimulationController`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/simulation/SimulationController.java), `currentState` is `volatile` for visibility, whereas buffer operations are `synchronized` for atomicity.

### Q23: Why are performance counters implemented using `AtomicLong` instead of synchronized long variables?
**Answer**: `AtomicLong` leverages hardware-level CPU primitives—specifically Compare-And-Swap (CAS)—to perform atomic increments and updates without thread context switching or lock contention overhead. Using CAS allows high-throughput operations on counters like hits, misses, and requests to complete in nanoseconds outside the engine lock. In [`CacheStatistics`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/stats/CacheStatistics.java), all counters are `AtomicLong`s, ensuring that recording statistics never slows down cache throughput.

### Q24: What is a daemon thread, and which services in this application run as daemons?
**Answer**: A daemon thread is a background service thread that does not prevent the JVM from exiting when all non-daemon user threads finish execution. When only daemon threads remain, the JVM terminates automatically. In our system, [`CacheExpirationService`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/expiry/CacheExpirationService.java) runs as a daemon thread to periodically sweep expired entries, and the history write-behind thread in [`PersistenceCoordinator`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/PersistenceCoordinator.java) is configured as a daemon thread.

### Q25: Why does the application use `DataOutputStream` rather than `ObjectOutputStream` for binary snapshots?
**Answer**: Standard Java Object Serialization (`ObjectOutputStream`/`ObjectInputStream`) is notorious for severe security vulnerabilities (remote code execution via gadget chains), brittle versioning issues, and significant payload bloat. By implementing [`SnapshotFileManager`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/SnapshotFileManager.java) using `DataOutputStream` and `DataInputStream`, we define an explicit, portable binary layout with a magic header (`0x4A435331`), versioning, raw field primitives, and an end-of-file CRC32 checksum, providing tamper-evident and safe serialization.

### Q26: How does the AWT Delegation Event Model work, and what are its three core components?
**Answer**: The Delegation Event Model separates event generation from event handling through three components: the Event Source (the UI component like a `Button` that generates the event), the Event Object (encapsulating event data, such as `ActionEvent` or `KeyEvent`), and the Event Listener (an object implementing a listener interface that receives the event). The source maintains a list of registered listeners and delegates event handling to them when an event occurs. In [`AwtEventConsole`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/awt/AwtEventConsole.java), button clicks generate `ActionEvent`s dispatched to an `ActionListener`.

### Q27: What is the purpose of adapter classes like `KeyAdapter` and `WindowAdapter`?
**Answer**: In Java AWT/Swing, listener interfaces often declare multiple abstract methods (for example, `KeyListener` declares `keyPressed`, `keyReleased`, and `keyTyped`). An adapter class is an abstract convenience class that provides empty default implementations for all methods in the interface. This allows developers to subclass the adapter and override only the specific methods they care about, avoiding boilerplate. In [`AwtEventConsole`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/awt/AwtEventConsole.java), `WindowAdapter` is subclassed to handle `windowClosing` alone.

## Unit 4: JDBC, Persistence, and Java Collections Framework

### Q28: What are the fundamental steps involved in connecting to a database and executing queries via JDBC?
**Answer**: The standard JDBC steps are: 1) Load the database driver (or let `DriverManager` auto-discover it via SPI); 2) Establish a `Connection` using `DriverManager.getConnection(url)`; 3) Create a `PreparedStatement` with a parameterized SQL query; 4) Bind parameters using setter methods (`setString`, `setInt`, etc.); 5) Execute the statement via `executeQuery()` or `executeUpdate()`; 6) Process the resulting `ResultSet`; and 7) Close all resources deterministically using try-with-resources. In our project, [`DatabaseManager`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/DatabaseManager.java) configures SQLite connections with WAL mode and foreign keys enabled.

### Q29: How does `PreparedStatement` prevent SQL injection attacks compared to `Statement`?
**Answer**: A plain `Statement` concatenates user input directly into SQL text, allowing attackers to inject malicious SQL commands that alter the query's AST (Abstract Syntax Tree). A `PreparedStatement` pre-compiles the SQL command structure into a template first and sends user inputs separately as parameterized values via `setString()` or `setLong()`. The database engine treats parameterized data strictly as literal values, never as executable code, completely immunizing against SQL injection. In [`SnapshotRepository`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/persistence/SnapshotRepository.java), all inserts and queries use `PreparedStatement`.

### Q30: How are atomic multi-row database transactions implemented in your repositories?
**Answer**: Atomic transactions are governed by disabling auto-commit on the JDBC connection using `connection.setAutoCommit(false)`. Multiple operations are executed and batched using `statement.addBatch()` and `statement.executeBatch()`. If all operations succeed, `connection.commit()` makes the changes permanent. If any `SQLException` is thrown, a nested `try` block calls `connection.rollback()` to undo all batch modifications before wrapping the exception in [`CachePersistenceException`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/exception/CachePersistenceException.java). Finally, `setAutoCommit(true)` is restored.

### Q31: Why is the cache engine kept in RAM rather than storing all active keys in SQLite?
**Answer**: An in-memory cache exists specifically to provide sub-microsecond access times (\(<1\,\mu\text{s}\)) for frequently accessed data. Even with fast SQLite WAL mode, database disk access requires disk seek, transaction locking, and IPC overhead, resulting in latencies of several hundred microseconds to milliseconds—over 1,000 times slower than RAM. SQLite is therefore utilized strictly for point-in-time snapshots, historical auditing, and benchmark persistence off the hot path, preserving peak cache performance in [`ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java).

### Q32: What are the differences between `HashMap`, `Hashtable`, and `ConcurrentHashMap`?
**Answer**: `HashMap` is unsynchronized, fast, and permits one `null` key and multiple `null` values, but is not thread-safe. `Hashtable` is a legacy synchronized collection that locks the entire table on every operation and rejects null keys/values, causing poor concurrency scaling. `ConcurrentHashMap` uses lock striping or fine-grained bucket CAS locks to allow high concurrent read/write throughput without locking the whole map. In [`CollectionsLab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/lab/CollectionsLab.java), we benchmark these collections side-by-side and clearly label `Hashtable` as legacy.

### Q33: How do `ArrayList`, `LinkedList`, and `Vector` compare in memory layout and access performance?
**Answer**: `ArrayList` is backed by a contiguous, resizable array providing \(O(1)\) random access by index and high CPU cache locality, but costs \(O(n)\) for mid-list insertions/deletions. `LinkedList` is a doubly linked list of node objects providing \(O(1)\) insertion/deletion at head/tail, but costs \(O(n)\) for indexed lookups and incurs substantial memory overhead per node pointer. `Vector` is structurally identical to `ArrayList` but synchronizes every method, making it a legacy collection with unnecessary locking overhead. In [`OperationHistory`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/history/OperationHistory.java), we use a bounded `LinkedList` for fast \(O(1)\) FIFO eviction from the front.

### Q34: What is a fail-fast iterator, and why does it throw `ConcurrentModificationException`?
**Answer**: A fail-fast iterator detects if its underlying collection is structurally modified (elements added, removed, or re-hashed) by any means other than the iterator's own `remove()` method during traversal. The collection tracks a `modCount` counter; if the iterator observes `modCount` changing during iteration, it immediately throws `ConcurrentModificationException` rather than risking non-deterministic behavior. In [`CollectionsLab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/lab/CollectionsLab.java), we demonstrate both the fail-fast exception and the correct removal pattern using `iterator.remove()`.

### Q35: Why is `TreeSet` used for LFU frequency ordering and the TTL expiry index?
**Answer**: `TreeSet` is backed by a Red-Black self-balancing binary search tree, maintaining its elements in sorted order with guaranteed \(O(\log n)\) cost for insertion, removal, and lookup of minimum/maximum elements. In [`LeastFrequentlyUsedPolicy`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/eviction/LeastFrequentlyUsedPolicy.java), `TreeSet` orders nodes by `(frequency, insertionSequence)`, making the lowest-frequency victim instantly accessible at `treeSet.first()`. In [`ExpiryIndex`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/expiry/ExpiryIndex.java), `TreeSet` orders entries by `(expiresAt, sequence)`, allowing the expiration daemon to purge expired items from the head of the tree without scanning the entire cache.

## Unit 5: JavaFX Desktop Architecture, Advanced Algorithms & System Design

### Q36: What is the JavaFX Application Thread, and what happens if heavy tasks run on it?
**Answer**: The JavaFX Application Thread is a single-threaded event loop responsible for processing UI input events, computing CSS and scene graph layouts, and rendering frames at 60 FPS. If heavy tasks (such as database queries, file I/O, or simulation loops) are executed on this thread, the UI event loop stalls, causing the window to freeze, stop repainting, and display the OS "Not Responding" spinner. In our architecture, all background work runs on worker threads, keeping the JavaFX Application Thread completely responsive.

### Q37: How do JavaFX `Task` and `Platform.runLater()` keep the desktop GUI responsive?
**Answer**: JavaFX `Task` extends `FutureTask` to run background computation on non-UI threads while providing observable properties and event hooks (`setOnSucceeded`, `setOnFailed`). When a background task completes and needs to update the UI scene graph, it schedules the update onto the JavaFX Application Thread using `Platform.runLater(Runnable)`. In [`PersistenceTab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/ui/PersistenceTab.java) and [`StatisticsTab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/ui/StatisticsTab.java), all database operations and benchmarks are wrapped in JavaFX `Task`s.

### Q38: How does the 250ms polling `Timeline` architecture prevent UI thread starvation?
**Answer**: During a high-throughput simulation processing 100,000 operations per second, calling `Platform.runLater()` for each individual cache operation would overwhelm the JavaFX event queue with hundreds of thousands of events, crashing or freezing the UI. Instead, we use a single JavaFX `Timeline` ticking once every 250 milliseconds. On each tick, the UI pulls a single immutable `StatisticsSnapshot` and `SimulationProgress` and updates the labels and charts in batch, bounding UI overhead to less than 1% CPU.

### Q39: What JavaFX visual effects and transforms are used in the dashboard and simulator?
**Answer**: Our interface utilizes four core JavaFX effects and transforms: 1) `DropShadow` is applied to all dashboard summary cards to provide modern elevation and depth; 2) `Glow` flashes on counter badges when cache sizes or hit counts change; 3) `Scale` creates a subtle pulse animation on the eviction counter when an entry is evicted; and 4) `Rotate` spins an activity indicator icon in [`DashboardTab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/ui/DashboardTab.java) and [`SimulatorTab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/ui/SimulatorTab.java) while a simulation run is actively executing.

### Q40: How do LRU, FIFO, and LFU eviction algorithms differ in victim selection?
**Answer**: Least Recently Used (LRU) evicts the item whose last access tick is oldest, rewarding frequently or recently refreshed keys using a `LinkedHashSet`. First-In-First-Out (FIFO) evicts the earliest inserted item regardless of how many times it was subsequently accessed, preserving pure chronological order. Least Frequently Used (LFU) evicts the item with the lowest total access count, resolving ties by evicting the earliest inserted among them using a `TreeSet` of `(frequency, sequence)`. In [`EvictionPoliciesWorkedExamplesTest`](file:///home/shivangi/projects/java-project/src/test/java/com/cse309/cache/eviction/EvictionPoliciesWorkedExamplesTest.java), all three policies are proven using the syllabus worked examples.

### Q41: How does wall-clock TTL expiration work, and why is `java.time.Clock` injected?
**Answer**: Each cache entry stores an absolute expiration epoch millisecond (`now + ttlMillis`). An entry is expired whenever `clock.millis() >= expiresAt`. A `TreeSet`-backed [`ExpiryIndex`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/expiry/ExpiryIndex.java) orders items by expiration time, and [`CacheExpirationService`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/expiry/CacheExpirationService.java) purges them in \(O(k)\) time where \(k\) is the number of expired items. By injecting `java.time.Clock` into [`CacheManager`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/app/CacheManager.java), tests can inject a `MutableClock` and advance time instantaneously, allowing unit tests in [`ExpirationTest`](file:///home/shivangi/projects/java-project/src/test/java/com/cse309/cache/expiry/ExpirationTest.java) to verify TTL without sleeping.

### Q42: What happens when the cache capacity is reduced while the cache contains more entries than the new limit?
**Answer**: If capacity is reduced from \(C_1\) to \(C_2\) where current size \(S > C_2\), the excess \(S - C_2\) entries must be evicted immediately and atomically under the cache lock. In [`ThreadSafeCache`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/core/ThreadSafeCache.java), `setCapacity()` identifies victims using the active eviction policy and records an `EvictionRecord` with reason `CAPACITY_REDUCED`. In the UI, [`ConfigurationTab`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/ui/ConfigurationTab.java) first calls `previewCapacityChange()` and presents a confirmation dialog informing the user of the exact number of entries that will be evicted.

### Q43: How does the thread-safe `BoundedBuffer` implement flow control between producers and consumers?
**Answer**: [`BoundedBuffer<T>`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/threading/BoundedBuffer.java) is a generic circular queue guarded by monitor synchronization. When a producer calls `put(item)` on a full buffer, it enters a `while (count == capacity) wait()` loop, suspending until space becomes available. When a consumer calls `take()`, it removes an item, decrements the count, and executes `notifyAll()`, signaling blocked producers to resume. This classic monitor pattern prevents producers from generating unlimited tasks into RAM, keeping memory usage bounded.

### Q44: What thread hygiene measures ensure clean application shutdown without leaked threads?
**Answer**: In [`CacheManager.shutdown()`](file:///home/shivangi/projects/java-project/src/main/java/com/cse309/cache/app/CacheManager.java), subsystems are stopped in a strict, cooperative sequence: 1) Active simulations are stopped by setting a stop flag, closing the buffer, and interrupting/joining workers; 2) The expiration daemon is interrupted and joined with a 2-second timeout; 3) The persistence history queue is closed, drained, and its worker thread joined; and 4) Database connections are closed. As verified in [`ShutdownTest`](file:///home/shivangi/projects/java-project/src/test/java/com/cse309/cache/app/ShutdownTest.java), zero non-daemon application threads remain alive after shutdown.
